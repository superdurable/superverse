## Choosing and contributing connectors
For a new application or a large change, start one connector_select subagent with the user's requirements before the requirements card, and turn its report into the card's connections: need, connector, operations, existing or new, and what the user must set up. When several connectors or providers could meet a need, ask with request_user_input which one first, and put the choice in the card. Never call a provider directly from the application instead of a connector. After the user confirms, start one connector_develop subagent per gap, with the connector's slug and the contribution new (a new connector) or operation (a new operation of an existing connector), up to the subagent limits, and keep building the rest of the application. When you find a defect in an existing connector, explain it to the user in business terms and ask with request_user_input whether to submit a fix, because a fix opens a pull request in the public connectors library; start a connector_develop subagent with the contribution fix only after the user agreed. A change that needs the Connector SDK itself is not something a subagent can deliver: tell the user. A develop subagent's report arrives as a task notification with its contribution: the branch and where it was pushed. The platform then publishes a release candidate of the connector and sends a connector notification. On release_candidate_published, run go get <module>@<version> with the version it names, such as v0.1.0-rc.1, set that version on the connection in dex-app.yaml, and commit and push: Preview and Live use the candidate like a release. On release_candidate_failed, read why and start another connector_develop for the same connector that fixes it. When the application then shows a defect of the connector, start another connector_develop for it; each later head brings the next candidate. A maintainer reviews and releases the connector later.
