# Run feedback

When a Run of the application in the Preview fails and that Run belongs to the current development,
the agent (platform or remote) learns of it the way it learns of a failed Preview deployment, and may
fix it in an automatic turn. This document owns that observation. It applies in both executor modes
and does not depend on remote mode.

## Scope

A Run is observed when one of these registers it:

| Registration | Who | Operation identity |
|---|---|---|
| A Run started from Studio's Preview Runs page (`FlowRunService.StartFlow` on a Preview target) | the Builder who started it | the StartFlow's `request_id`, which Studio generates per start |
| "Watch this Run" on any Preview Run page (`FlowRunService.ObserveFlowRun`) | the Builder who clicked | the `request_id` of that call, generated by Studio per click |
| The agent's tool `watch_preview_run(flow_id, run_id)`, for a Run it started or found (for example through `read_platform_flow` or `dexcli`) | the agent; the actor of the turn's input is recorded as the requester | `agent-<CallID>` of the tool call |

Not observed: Live Runs, and Preview Runs nobody registered (triggers, child Flows, the
application's own restarts). "Ask the agent about this Run" on any Run page fills the composer with
the Flow's identity and its failure summary; the Builder sends it as an ordinary message.

## Identity

- **The observation's identity is the registering operation's identity** (the table above). A retry of
  the same operation finds the same observation and changes nothing; a new operation is a new
  observation. No counter is needed, and the identity survives the observation's deletion.
- **The observed target is the exact Run**: `{FlowID, RunID}` of the application's Flow in the
  Preview's own Dex. Only the exact Run makes a failure visible after a rapid rerun of the same
  FlowID. The wait is Dex's completion wait, the generated RPC `WaitForFlow` (`WaitForFlowRequest
  {flow_id, run_id, needs_results, wait_time_seconds}`), which waits for that Run's result and
  answers its status, error type and message (server v1.6.1, `server/service/api/service.go`,
  `WaitForFlow` calling `GetWorkflowResult` with both IDs). The SDK's convenience wrapper
  `dex.Client.WaitForFlow` passes no RunID, so the watch calls the generated client directly. This is
  a client call from an Execute, not a Flow Step's `WaitFor`. A second
  registration of a target that already has an active observation returns that observation.
- **Rule exception.** AGENTS.md keeps Dex RunIDs out of RPC input and identities except for
  engine-history diagnostics. This feature carries the RunID of an *application* Run, in the
  application's own engine, only as the target of an engine wait, as Studio's Flow API diagnostics
  already use RunIDs to read application history. The exception names that boundary exactly: the RunID of a Run in an
  application's engine may be the target of an engine wait or read by the code that observes that
  engine (Studio's Flow API and PreviewFlow's Run observation). No Superverse Flow's RunID is
  involved, and no business identity, notification ID, Stream cursor or external-effect identity
  contains it. RUNFEEDBACK adds this
  sentence to AGENTS.md, CLAUDE.md and `.cursor/rules/planning.mdc`.
- **Notification ID**: `run/<observation identity>`, so a repeated notification is absorbed by the
  Session's receipts.

## Where the observation lives

The observation belongs to `PreviewFlow`, not to the Session:

- The observed Runs live in the Preview engine of one Sandbox instance, which `PreviewFlow` already
  tracks (the instance, its WorkspaceRequestID and generation). When the Preview's instance changes,
  its observations end under the same fence.
- `PreviewFlow` already reports outcomes to the Session through `SessionFlowService` and the
  Session's `ReportSessionNotification`. A failed Run is one more delivery outcome on that path, so
  the Session gains no primitive and no Step, and its message handling is never blocked by a wait.

## How it works

1. **Registration.** Each path calls `SessionFlowService.ObserveRun(projectID, observationID,
   target, requester)`, which calls the `PreviewFlow` RPC `ObserveRun` with the instance the Run
   belongs to. The StartFlow path retries up to three times within 5 seconds after a successful
   start and answers `StartFlowResponse.agent_watch` (`WATCHED`, or `NOT_WATCHED` with `capacity`,
   `unavailable` or `instance_changed`). The authoritative state is the observation in the Preview
   snapshot, which the Run page reads; a Run that is not watched offers "Watch this Run". The agent's
   tool returns the same answer as its result.
2. **Admission.** `ObserveRun` holds PreviewFlow's existing `CommandLock`. It writes the observation
   with its business lease (`ExpiresAt` = now + `sandbox.runObservationWindow`), increases
   `RunWatchGeneration`, and returns `CancelSteps(WatchRuns)` with a new `WatchRuns(generation)`
   movement. A running `WatchRuns` Execute sees only its invocation's Attributes, so the restart is
   how it learns of the new observation; the cancelled one made no effect and lost only an open long
   poll.
3. **Watching.** `WatchRuns(generation)` is one Execute with `dexflow.PollUntil(ctx, 1s, 40s, check)` and
   no lock. It reads `ObservedRuns` once, at its start. Each round calls, for every active observation
   (at most 4, in parallel), `WaitForFlow` on the exact Run with `wait_time_seconds` 30, through the
   Sandbox Service's existing Dex connection. A Run still running answers the long poll's timeout; a
   closed Run answers its status and error. The check is done as soon as a Run closes, a lease passes,
   or the Sandbox does not answer. There is no cursor and no history replay: the wait is idempotent,
   so every round, restart and retry asks the same question again. It returns what it found per
   observation identity.
4. **Settling.** The following short Step `SettleRunObservations(generation, findings)`
   (`stateStepOptions`, holding `CommandLock`) reads `ObservedRuns`, the current instance and
   `RunWatchGeneration` again, fresh. It applies a finding only to the observation with the same
   identity that is still active and still of the current instance:
   - a failed Run sends one delivery notification through the existing Service call and ends `failed`;
   - a completed Run ends `completed` silently;
   - a passed lease ends `expired`; an unanswering Sandbox ends `unreachable`; an observation of an
     instance that is no longer current ends `instance_changed`.

   It returns to `WatchRuns` only when its
   `generation` equals `RunWatchGeneration` and active observations remain; a Settle of an older
   generation, whose watch `ObserveRun` already replaced, applies its findings and ends, so two
   watches never run at once.
5. **Leases and engine limits.** The business lease (`ExpiresAt`, per observation) decides when an
   observation ends, whatever happens to the Execute that watches it. The engine limit,
   `PollingStepOptions(sandbox.runObservationWindow + 5 min)`, is only a safety net for one Execute: a
   restart by `ObserveRun` starts a new Execute with a fresh limit, which cannot extend any
   observation, because the leases are stored. When the safety net is passed, the Execute failure
   route goes to `SettleRunObservations`, which ends what has expired and restarts the watch for the
   rest.
6. **Restart and recovery.** A Worker restart reruns `WatchRuns`, whose first round asks each Run for
   its result again; a closed Run answers at once and a repeated notification is absorbed by its ID.
   No round needs a durable write.

Why `PollUntil` rather than a `WaitFor`: the Run lives in the application's own Dex in the Sandbox,
an external system to PreviewFlow, and AGENTS.md requires waiting for an external system in one
long-running Execute through `dexflow.PollUntil`; a `WaitFor` may wait only for the Flow's own
Channels, RPCs and business timers. Each round is the completion long poll itself (no
fixed-interval status read), the round timeout (40 s) covers the 30 s wait, and the Step needs no browser and holds no
lock, so it never delays the Session or PreviewFlow's commands. The pinned SDK (v1.12.0) gives an
Execute no way to refresh Attributes, and a heartbeat's details are not an Attribute commit, so every
decision that depends on current state is made in `SettleRunObservations`, under the lock, from a
fresh read.

## What the agent receives

A `delivery` notification with the new source `run`: owner `application`, code `RUN_FAILED`, the
Preview's commit, the Flow type, FlowID and RunID, the failed Step and the failure's type, who
registered the observation, and a message of at most 2 KiB. The failure text comes from the
application and possibly from its end users, so it is framed as data ("the Run reported:") after the
existing notification preamble, truncated, and never contains Flow inputs or Attribute values. The
existing rules apply: a failure whose commit is not HEAD becomes a notice; only an
application-owned failure at HEAD opens an automatic turn, within `agent.platformTurns`.

## Dex Flow Changes

### PreviewFlow

- **Identity and lifecycle**: unchanged (`preview-<projectID>`, completed only by Project deletion).
- **AttributeMap `ObservedRuns`** (new): key = the observation identity, path-escaped (for example
  `7f3c…` for a Studio request ID or `agent-toolu_01…`); value `runwatch.Observation{Target{FlowID,
  RunID}, Instance (WorkspaceRequestID and generation), Requester conversation.Actor, Source (start,
  watch, agent), RegisteredAt, ExpiresAt, Status (active, failed, completed, expired,
  unreachable, instance_changed, refused), Failure}`. No cursor is stored.
  - **Bounds**: at most 4 active and 16 retained; an ended observation is deleted after 24 hours or,
    oldest first, when the 17th would be stored. Loaded whole (at most 16 small instances) by
    `ObserveRun`, `WatchRuns`, `SettleRunObservations` and the snapshot.
- **Attribute `RunWatchGeneration`** (new, `uint64`, written under `CommandLock`): which `WatchRuns`
  is current. Needed because a Settle of a replaced watch can run after `ObserveRun` restarted the
  watch; without it that Settle would start a second watch.
- **RPC `ObserveRun`** (new, write, `ShortRPC` with `CommandLock`): admits an observation for the
  current instance only and answers `instance_changed` for another; idempotent for the same identity;
  returns the active observation of the same target; refuses `capacity` beyond 4 active or the
  replica's watch cap. Increases `RunWatchGeneration` and returns `CancelSteps(WatchRuns)` and a
  `WatchRuns` movement.
- **Steps** `WatchRuns` (polling Execute, no lock, reads only its invocation snapshot) and
  `SettleRunObservations` (short Execute with `CommandLock`; one Service call per failure, idempotent
  by notification ID), which is also `WatchRuns`' Execute failure route.
- **Channels, ChannelMaps, Streams**: none.

### SessionAgentFlow

- `conversation.NotificationSource` gains `run`; the Session's notification handling is unchanged.
- The agent tool `watch_preview_run` is a platform tool (no Sandbox, no workspace lease) that calls
  `SessionFlowService.ObserveRun` from its Execute, like `start_agent` reaches the Session Service.
  AGENTS.md's list of the Session's Flow RPCs gains "the registration of a Preview Run the agent asks
  to watch"; RUNFEEDBACK updates the three rule files.

## Tests

- Dex integration on the lane: a Studio-started Preview Run fails, the Session receives one
  `delivery`/`run` notification and opens an automatic turn (mock scenario `run-failure-fix`, with a
  reply that declares `notification: delivery`); a completed Run reports nothing.
- The agent's `watch_preview_run` (mock scenario `watch-preview-run`): the agent starts a Run, watches
  it, and receives its failure.
- Registration: a failed `ObserveRun` after a successful start answers `NOT_WATCHED` and "Watch this
  Run" recovers it; a retried registration with the same identity changes nothing; a rapid rerun of
  the same FlowID: the first Run's failure is still reported, because the target is the exact Run.
- Watch races: an observation added while `WatchRuns` runs is watched after the restart; a Settle of
  the replaced watch generation applies its findings and starts no second watch; a finding for an
  observation that was replaced or ended is not applied.
- Instance change and an unreachable Sandbox end observations at once; a Worker restart during
  `WatchRuns` asks again and reports once; the bounds of 4 active and the replica cap.
- `WaitForFlow` with both IDs on the Preview engine's pinned `dexcli dev` (re-verified at RUNFEEDBACK
  start, as on server v1.6.1).
- `make check-mock-scenarios` covers both scenarios and the new tool.

## Resource Scalability

- **Unit**: one `WatchRuns` Execute per Project that has active observations, with at most 4 completion
  waits (30 s) against that Project's own Sandbox Dex, not the platform Dex. The Execute holds one platform
  Worker execution slot while it runs.
- **Window**: an observation's lease is `sandbox.runObservationWindow` (default 30 minutes, range
  1 minute to 2 hours), so a Project holds the slot only while a registered Run is young.
- **Cap**: each server replica runs at most `sandbox.maxRunWatches` concurrent `WatchRuns` Executes
  (default 200, range 1 to 2,000), counted in process because the slot is that replica's Worker's.
  When the cap is reached, the Execute marks the new observations `refused` (reason `capacity`) and
  ends; the Run itself is unaffected, and the Run page says the agent will not be told about it.
- **At 10,000 Projects**: the slots in use equal the Projects with a registered Run younger than the
  window. Even if every Project registered one Run per hour, that is about 5,000 concurrent watches
  with a 30-minute window, so the cap, not the Project count, bounds each replica; refused
  observations are visible and the agent can still be asked about any Run.
- **Hot path**: no control-plane call; no scan across Projects. The map is bounded at 16 instances.
